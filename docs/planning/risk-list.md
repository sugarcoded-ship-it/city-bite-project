# Risk List

| Risk | Impact | Likelihood | Mitigation |
|------|--------|------------|-----------|
| **Order flow business logic complexity** — Edge cases in status transitions (Pending → In Preparation → On Delivery → Delivered, no separate "Ready" step), and who can update what, were a stated blocker in Sprint 3. Unresolved logic leads to backend rework. | High | High | Resolve and document all allowed status transitions explicitly before building the API. Enforce them in the service layer, not just the frontend. |
| **Frontend–backend integration gaps** — Frontend and backend have been developed in parallel without a fully finalized API contract. Field name mismatches or missing fields at integration time cause significant debugging overhead. | High | High | Agree on and document request/response shapes for all core endpoints before continuing parallel implementation. Use a shared contract file or Swagger spec to reduce guesswork. |
| **Unfamiliar frameworks slowing delivery** — Several team members are still building comfort with Kotlin/Spring Boot and React/TypeScript. This reduces implementation speed and increases the chance of subtle bugs. | High | High | Maintain regular pairing sessions so more experienced members can unblock others. Prioritize completing core features before exploring new patterns. |
| **Keycloak JWT not attached correctly on protected routes** — If the frontend does not include the Authorization header on staff API calls, all protected endpoints will return 401 errors. Debugging auth issues mid-integration is time-consuming. | High | Medium | Implement and test the Authorization header pattern on one protected endpoint first. Verify token flow end-to-end before wiring up the full staff dashboard. |
| **Scope creep under deadline pressure** — The implementation deadline is the end of Week 10 (approximately 5 July 2026). Adding small "nice to have" features absorbs time that is already very limited. | High | Medium | Treat the in-scope list in the product brief as a hard boundary. Any addition must explicitly displace something of equivalent complexity. |
| **Deadline with remaining features incomplete** — Today is 1 July 2026 and the deadline is ~5 July 2026. The Pending Order page and several UI decoration tasks are still in progress as of Sprint 4. | High | High | Prioritize completing end-to-end core flows (place order → staff sees it → status update → customer tracking) over polish. Defer UI styling until core logic is verified. |
| **Merge conflicts from parallel feature development** — Multiple team members are simultaneously completing features targeting the same files (routes, API client, shared components). Merge conflicts slow down final integration. | Medium | High | Coordinate through short daily syncs. Use feature branches with small, focused PRs. Merge frequently to prevent large divergences from accumulating. |
| **Data validation mismatch between routes and backend responses** — Sprint 4 notes confirm discrepancies between mapped frontend routes and actual backend response shapes. These cause runtime errors that are hard to trace without full-stack visibility. | Medium | High | Manually test each route end-to-end against the live backend before marking a feature as done. Cross-reference backend response DTOs against frontend type definitions. |
| **Keycloak infrastructure dependency failure** — Keycloak must be running as a Docker service during development and in the demo environment. If the realm configuration is missing or misconfigured, staff and owner login are completely broken. | High | Medium | Keep the `realm-config.json` in version control and document the import steps in the runbook. Test the full Keycloak setup from scratch on a clean machine before the demo. |
| **Logic alignment across user roles** — Customer, staff, and owner views all interpret the same order data differently. If the backend returns the same status in different formats per role, the UI will display incorrect states. | Medium | Medium | Define a single canonical order state model shared across all roles. Review role-specific API responses together to confirm they use consistent field names and values. |
| **Menu item without recipe data silently skips stock deduction** — *(Updated after ADR 002-D)* Automatic stock deduction is now implemented, so this risk is largely mitigated for items with recipe data. The remaining risk is narrower: a menu item with no `Menu_Recipe` rows mapped will deduct nothing on order acceptance, silently falling back to manual availability toggling for that item only. | Low | Medium | Audit menu items for missing recipe/option-ingredient mappings before the final demo. Train staff to still manually toggle availability for any item known not to have recipe data configured. |
| **ETA drift and a paid external dependency** — *(New, post ADR 002-E)* ETA is a flat 15-minute prep-time constant plus a Google Routes API travel-time estimate and a 10-minute buffer — not a recipe-based or live-kitchen-load estimate — and can drift during busy periods or unusually large orders. It also depends on a paid, keyed Google Maps Platform account (Geocoding + Routes APIs) whose key is currently hardcoded in `docker-compose-local.yml` rather than in an untracked `.env`. | Medium | Medium | Set expectations in the demo that ETA is an estimate, not a guarantee. Rotate and move the Google Maps API key into `.env` before wider distribution of the repo (see known-issues.md). |
| **Demo environment setup failure** — The demo depends on Docker Compose bringing up PostgreSQL, Keycloak, NGINX, frontend, and backend simultaneously and in the correct order. A misconfigured environment on demo day means the entire system cannot be shown. | High | Low | Perform a full end-to-end rehearsal on a clean machine at least 48 hours before the demo. Document all required `.env` values and Keycloak realm import steps in the runbook. |
| **Academic deliverables falling behind code delivery** — Documentation (product brief, ADRs, sprint notes, architecture page, handover materials) is part of the graded output and must be kept current alongside working code. | Medium | Medium | Assign documentation tasks alongside implementation tasks in each sprint. Do not leave all documentation to the final week. |
| **UI styling backlog blocking demo readiness** — Sprint 4 confirms the Owner staff detail page still requires complete visual layout and decoration. Incomplete or inconsistent UI reduces perceived quality during graded demonstration. | Medium | High | Assign styling tasks with specific due dates (per Sprint 4 action items). Complete functional logic first, then layer on styling, so blocking is minimized. |
| **Single point of knowledge for critical components** — Certain areas (e.g., Keycloak configuration, database schema, specific backend modules) may be deeply understood by only one team member. If that person is unavailable, the team is blocked. | High | Low | Hold short knowledge-sharing sessions after each major component is completed. Ensure at least two people can explain and modify each critical component. |
